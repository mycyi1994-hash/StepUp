# 서버 스키마

Supabase(Postgres) 에 올릴 표와 권한 규칙입니다.

> 프로젝트를 아직 안 만드셨다면 [`docs/SETUP-BACKEND.md`](../docs/SETUP-BACKEND.md) 먼저 보세요.

---

## 올리는 법

**[`setup.sql`](setup.sql) 하나만 붙여넣으면 됩니다.**

1. Supabase 대시보드 → 왼쪽 **SQL Editor** → **New query**
2. `setup.sql` 전체를 복사해 붙여넣기
3. **Run**

### 이미 한 번 올리셨다면?

**그냥 다시 붙여넣고 Run 하세요.** 몇 번을 다시 해도 안전합니다.

이미 있는 표는 건너뛰고, 새로 생긴 표와 달라진 규칙만 반영됩니다. **쌓인
기록은 지워지지 않습니다.** 스키마가 늘어날 때마다 "이번엔 어디부터 붙여넣어야
하지"를 따지지 않아도 되게 만들어 둔 것입니다.

> 전체가 하나의 트랜잭션입니다. 중간에 실패하면 아무것도 바뀌지 않습니다 —
> 반쯤 적용된 상태로 남지 않습니다.
>
> 스키마를 고칠 때는 `migrations/` 쪽을 고치고 `scripts/build-setup-sql.py` 로
> `setup.sql` 을 다시 만듭니다.

### 매번 붙여넣기 싫다면 — 자동 적용

GitHub 저장소 **Settings → Secrets and variables → Actions → New repository
secret** 에 한 번만 넣어 두면, 이후로는 main 에 합쳐질 때마다
`.github/workflows/deploy-sql.yml` 이 `setup.sql` 을 대신 올립니다.

- 이름: `SUPABASE_DB_URL`
- 값: Supabase 대시보드 위쪽 **Connect** → **Session pooler** 의 연결 문자열
  (`postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-...pooler.supabase.com:5432/postgres`),
  `[YOUR-PASSWORD]` 를 데이터베이스 비밀번호로 바꾼 것. **Direct connection 주소는
  GitHub 에서 닿지 않습니다.**

비밀이 없으면 이 작업은 건너뛰기만 합니다. 지금 것을 바로 올리려면 Actions →
**Deploy server schema** → **Run workflow**.

## 설계에서 가장 중요한 것

### 앱이 금액을 정하지 않는다

앱에는 `anon` 키가 박혀 있습니다. 그 키는 APK 를 뜯으면 누구나 꺼낼 수 있습니다.
그래서 앱이 "나 500 SUP 벌었어"라고 보내면 그대로 믿는 구조여서는 안 됩니다.

원장(`sup_ledger`)과 세션(`walk_sessions`) 표에는 **앱이 직접 쓸 수 없습니다.**
권한을 회수했고, 행 단위 보안(RLS)에도 쓰기 정책이 없습니다. 기록은 오직
두 함수로만 들어옵니다.

| 함수 | 하는 일 |
|---|---|
| `record_session(...)` | 세션을 받아 **서버가 직접 적립액을 계산**한다. 앱이 보낸 금액은 받지도 않는다 |
| `spend_sup(...)` | 잔고를 확인하고 차감한다. 동시 요청이 겹쳐도 음수가 되지 않게 잠근다 |

### 속도도 앱에게 묻지 않는다

순위표에 "최고 속도" 부문이 있습니다. 그 값을 앱이 보내게 두면, 그 순위는
달리기가 아니라 타자 실력을 재게 됩니다. 서버가 올라온 GPS 경로에서 직접
계산합니다 (`economy.track_speed_stats`).

10초 이상 떨어진 두 점으로 구간 속도를 잽니다. 1초짜리 구간으로 재면 GPS 가
몇 미터 튀는 것만으로 시속 수십 km 가 나오기 때문입니다. 구간의 절반 이상이
시속 60km 를 넘으면 그건 GPS 오류가 아니라 타고 간 것으로 보고 VOID 판정합니다.

### 잔고를 따로 저장하지 않는다

`sup_balances` 는 표가 아니라 원장의 **합계**입니다. 잔고를 따로 들고 있으면
원장과 어긋날 수 있고, 어긋났을 때 어느 쪽이 맞는지 알 방법이 없습니다.
합이 곧 잔고라면 어긋날 수가 없습니다.

### 같은 세션이 두 번 적립되지 않는다

지하철에서 업로드하면 응답을 못 받고 앱이 재시도합니다. `(사용자, 시작시각)`
에 유일 제약이 있어, 재시도는 **원래 결과를 그대로 돌려줄 뿐** 새로 적립하지
않습니다.

### 하루 상한은 "적립된 걸음"으로 센다

걸은 걸음이 아니라 실제로 인정된 걸음(`rewarded_steps`)을 더합니다. 걸은 걸음으로
세면, 상한에 걸려 인정되지도 않은 몫이 상한을 깎아 다음 세션이 손해를 봅니다.

### 커뮤니티: "내가 눌렀는지"는 칸이 아니라 계산이다

폰 안에서는 글에 `liked`, `joined`, `mine` 같은 칸이 붙어 있었습니다. 서버에서는
그럴 수 없습니다 — 같은 글이라도 **누가 보느냐에 따라 답이 다르기** 때문입니다.
그래서 별도의 표(`post_likes`, `flash_participants`)로 두고, 보는 사람 기준으로
계산해 `post_feed` 뷰 한 줄에 담아 내려줍니다.

### 정원이 있는 일은 함수로만

번개러닝 참가는 `join_flash()` 로만 들어옵니다. 참가자 표에 직접 INSERT 하면
정원을 지킬 수 없습니다 — 두 사람이 마지막 한 자리를 동시에 노리면 둘 다
"자리 있음"을 보고 둘 다 들어갑니다. 함수가 글을 잠그고 셉니다.

### 랭킹 뷰만 RLS 를 지나간다

다른 뷰에는 `security_invoker = true` 를 붙여 "읽는 사람 권한으로" 보게 했습니다.
랭킹은 반대여야 합니다 — 남의 세션은 가려야 하지만 순위는 남들과 비교해야
나오니까요. `runner_stats` 뷰는 소유자 권한으로 돌지만, **앱에는 열어 주지
않습니다.** 앱은 `leaderboard()` 함수로만 접근하고, 그 함수는 상위 몇 명과
내 줄만 돌려줍니다. 원본 행 — 언제 어디를 뛰었는지 — 은 여전히 본인만 봅니다.

## 검증

```bash
supabase/tests/run.sh
```

로컬 Postgres 16 을 띄워 **깨끗한 데이터베이스에 `setup.sql` 을 두 번 올린 뒤**,
앱과 같은 권한(`authenticated`)으로 규칙을 하나씩 두드려 봅니다. 60여 개 항목
중 하나라도 어긋나면 그 자리에서 멈춥니다.

확인하는 것:

| 갈래 | 내용 |
|---|---|
| 적립 | 금액 계산, 중복 재전송, 케이던스 조작, 차량 이동, 하루 상한 |
| 속도 | 경로에서 읽은 속도가 맞는지, 깨진 경로에 죽지 않는지 |
| 소비 | 잔고 부족, 소비 함수로 적립 시도 |
| 권한 | 원장·세션 직접 쓰기, 남의 기록 조회, 남의 프로필 수정 |
| 커뮤니티 | 크루 글 가림, 남의 이름으로 쓰기, 정원 초과, 차단, 신고 |
| 랭킹 | 합계 뷰 직접 읽기, 내 줄 포함, VOID 세션 제외 |

> 권한 검사는 실제 Supabase 와 같은 조건(테이블 권한이 `authenticated` 에
> 부여된 상태)에서 합니다. 권한이 없는 상태로 검사하면 RLS 가 아니라 권한
> 부족으로 막혀서, 정작 RLS 가 동작하는지는 확인되지 않습니다.

## 아직 앱이 안 쓰는 것

커뮤니티·랭킹 표는 만들어졌지만 **앱은 아직 폰 안의 Room 을 봅니다.** 서버로
옮기는 것은 다음 작업입니다. 먼저 표와 규칙을 확정해 두는 이유는, 화면을
고쳐 놓고 나서 스키마를 바꾸면 양쪽을 두 번 고치게 되기 때문입니다.
