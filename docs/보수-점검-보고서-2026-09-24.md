> 업로드 일꾼·러닝 서비스·걸음 센서·푸시, 그리고 앱이 부르는 서버(`supabase/migrations`)와

가장 심각했던 것:

1. **서버: 로그인한 사람 누구나 `market_settle` 을 직접 불러 SUP 를 만들고 남의 신발을 가져갈 수 있었다.**
   `revoke ... from public` 만 해 두어, Supabase 가 따로 붙이는 `anon`·`authenticated` 실행 권한이 남아 있었다.
   로컬 검사 환경이 이 기본 권한을 흉내 내지 않아 기존 검사도 통과했었다.
2. **서버: `record_session` 이 앱이 보낸 시작 시각·운동 시간을 그대로 믿었다.** 2001년 날짜로 세션을
   지어 올리면 날마다 하루 상한이 새로 열렸고, 운동 시간을 0 으로 적으면 케이던스 검사를 건너뛰었다.
3. **서버: 순위 재료(최고 속도·누적 거리)·일별 걸음·코스 달린 횟수를 표에 직접 쓸 수 있었다.**
4. **앱: 에너지 상한이 화면과 실제 계산에서 달랐다.** 신발을 강화해도 벌 수 있는 걸음이 늘지 않았다.
5. **앱: 올리지 못한 러닝이 다음 러닝을 끝낼 때까지 잠들었다.** 로그아웃 중이었거나 10개가 넘게
   쌓이면 7일 청구 창을 넘길 수 있었다.

## 1. 서버(Supabase) — 고친 것

모두 기존 마이그레이션 파일을 고쳤고 `scripts/build-setup-sql.py` 로 `supabase/setup.sql` 을 다시 만들었다.
`setup.sql` 은 이미 올린 DB 에 **다시 붙여넣어도 안전**하다(깨끗한 DB 와, 원래 `setup.sql` 을 올린 DB 위에
새 파일을 덧붙인 경우 둘 다 검사).

## 5. 찾았지만 고치지 않은 것 — 결정이 필요함

"보수만, 새 개발은 하지 않는다"는 원칙에 따라, 고치려면 설계를 바꾸거나 새 저장소·새 표가 필요한 것은
손대지 않았다.

| # | 내용 | 고치지 않은 이유 / 권하는 방향 |
|---|---|---|
| X1 | **로컬 SUP 원장은 서버 확인 없이 쌓인다**(세션 정산·백그라운드 걸음·코스 완주·환영 보상). 서버 금액과도 다르다(앱은 XP 부스터 ×2·에너지 상한 적용, 서버는 미적용·일 48,000보 상한). | README 가 밝힌 설계("SUP 는 첫 순간부터 로컬에서 적립·소비")라 구조를 바꾸지 않았다. 문구는 "적립 완료"를 쓰지 않는다. 서버 잔고를 정본으로 할지 결정이 필요 |
| X2 | 서버가 앱이 보낸 **파티 인원**(최대 +50%)을 믿는다 | 참가자는 러닝이 끝나면 방에서 나가(`party_leave`) 기록이 지워지므로, 검증하려면 "파티 러닝 이력" 표가 새로 필요 |
| X3 | 어테스터: 같은 러닝을 시작 시각만 바꿔 여러 번 서명받을 수 있고, 러너별 일일 상한·호출자 인증이 없다 | 저장소(KV/Durable Object)·인증이 새로 필요. 현재 앱은 어테스터를 부르지 않는다(`AttesterClient` 호출부 없음) — 온체인 정산 전에 꼭 필요 |
| X4 | 게시글·크루를 표에 직접 INSERT 하면 `post_create`·`crew_create` 의 도배 제한·크루 10개 상한을 건너뜀 | 서버 검사 코드가 이 직접 쓰기에 기대고 있어 함께 고쳐야 함 |
| X5 | 로그인 refresh token 이 안드로이드 백업에 포함됨 | 설정 파일만 백업에서 빼면, 복원 때 로컬 원장은 돌아오고 거래소 커서는 없어져 **거래 줄이 다시 들어와 잔고가 부풂**. 세션을 별도 파일로 옮기는 작업이 필요 |
| X6 | 일일 상한·땅따먹기 "하루"가 UTC 기준(한국 09:00 에 바뀜), 앱·이벤트는 현지 기준 | 바꾸면 전환일에 상한이 두 번 열림 — 운영 판단 필요 |
| X7 | 거래소에 올린(LISTED) 신발도 폰에서 착용·강화 가능 | 폰에 판매 중 상태가 없어 새 필드가 필요 |
| X8 | 거래 가능 잔고를 못 읽으면 0 으로 표시 | 화면 문구 변경이 필요(디자인 범위) |
| X9 | 에너지가 가득 찬데도 에너지 셀(50 SUP)을 살 수 있음 | 막으려면 새 안내 문구(4개 언어)가 필요 |
| X10 | 로그아웃 뒤 다른 계정으로 로그인하면 거래소 동기화 커서가 앞 계정 것으로 남음 | 현재 로그아웃 경로는 계정 삭제뿐이라 드묾. 커서를 사용자별로 나누는 작업 필요 |
| X11 | 파티 방장이 앱을 강제 종료하면 서버에서 방장이 넘어가지 않음 / 강퇴된 사람이 다시 들어올 수 있음 | 서버 쪽 오래된 멤버 정리·강퇴 목록이 새로 필요 |
| X12 | `market_buy_now` 와 `market_sell_now` 가 같은 신발을 반대 순서로 잠가 드물게 교착(Postgres 가 한쪽을 취소) | 기존부터 있던 것. 한쪽 실패로 끝나고 데이터는 안전 |
| X13 | 첫 걸음 측정값이 세션 기준점으로 쓰이기 전 아주 짧은 경합 | 순서를 바꾸면 더 나쁜 경합(하루 걸음이 세션에 통째로 들어감)이 생겨 그대로 둠 |
| X14 | `push-send` 의 FCM 호출에 시간 제한이 없음 | 2분 넘게 걸리면 드물게 중복 발송 가능 |

## 7. 반영하려면

- **서버**: 고친 `supabase/setup.sql` 을 Supabase SQL 편집기에 다시 붙여넣는다(재적용 안전).
  S1(체결 함수 권한)은 앱 업데이트와 무관하게 서버만 바꾸면 막힌다 — 가장 먼저 반영을 권한다.
- **앱**: main 에 합쳐 CI 가 새 APK 를 만들어야 사용자 앱이 바뀐다. DB 스키마 버전은 그대로(11)라
  마이그레이션이 필요 없다. `strideup.db`·`strideup_prefs` 이름은 바꾸지 않았다.
- 순서: 서버를 먼저 올려도 옛 앱과 호환된다(옛 앱은 막힌 표에 직접 쓰지 않는다).
