## 아이템

| 종류 | 이름 | 효과 | 언제 |
|---|---|---|---|
| `RUN_BOOSTER` | 러닝 부스터 | 고른 러닝 1회 적립 × 1.5 | 출발 전에 고른다 |
| `REWARD_DOUBLE` | 보상 2배권 | 고른 러닝 1회 적립 × 2 | 출발 전에 고른다 |
| `ENERGY_DRINK` | 에너지 드링크 | 고른 러닝 1회 에너지를 절반만 | 출발 전에 고른다 |
| `DURABILITY_RESET` | 내구도 초기화권 | 신발 내구도를 가득 | 바로 쓴다 |
| `ENERGY_RESET` | 하루 할당량 초기화권 | 오늘 쓴 에너지를 되돌린다 | 바로 쓴다 |

- 값(1.5 · 2 · 0.5)은 `economy.item_kinds.value` — 배포 없이 바꾼다(SQL Editor: `update economy.item_kinds set value = 1.3 where kind = 'RUN_BOOSTER';`).
  다시 배포해도 운영 중 바꾼 값을 덮지 않는다. 끄기는 `enabled = false`.
- **하루 할당량 = 하루 에너지**(기본 10칸 = 6,000보)다. 하루 금액 상한(600 SUP) · 걸음 상한(48,000) · 올린 날 상한은 부정 방지 선이라 그대로다.
- **같은 종류는 겹치지 않는다**: 러닝 부스터와 보상 2배권은 같은 묶음(`REWARD`)이라 한 러닝에 하나만 고른다(서버가 거절).
  적립 배수는 24시간 부스터(× 2) · 보상 이벤트 · 러닝 아이템 가운데 **가장 큰 것 하나**만 적용한다(`economy.run_reward_mult`) — 곱하지 않는다.
- 가득 찬 신발 · 오늘 쓴 에너지가 없을 때는 초기화권을 쓰지 않는다(아이템이 사라지지 않는다).
- 러닝 아이템은 출발할 때 가방에서 빠진다. 무효 러닝은 효과가 없고 돌려주지 않는다. 크루 러닝에는 적립 배수만 적용된다(크루 러닝은 개인 에너지를 쓰지 않는다).
- 유효기간 · 유저끼리 주고받기 · SUP 로 사기는 없다(정해지지 않았다).

## 앱이 부르는 함수

| 함수 | 하는 일 |
|---|---|
| `items_me()` | 종류마다 개수(0 개도) · 값 · 쓰는 때, 지금 켜진 보상 이벤트, 24시간 부스터가 끝나는 때 |

- 러닝 기록의 `walk_sessions.reward_mult` 에 적용된 배수가 남는다(결과 화면용).

## 운영자 페이지 — `stepupcrew.com/ops/`

운영자 키로 **로그인**한다(2026-11-18 서버 0114 — 아래 "운영자 페이지 보안"). 서버에는 키 · 세션 모두 해시만 있고,
페이지는 키를 로그인에만 보내고 탭에는 세션 번호만 둔다.

```sql
select economy.ops_key_new('담당자 이름');       -- 한 번만 보이는 키, 30일
select economy.ops_key_new('담당자 이름', 90);   -- 날 수를 정해서(1 ~ 365)
update economy.ops_keys set expires_at = now() + interval '30 days' where label = '담당자 이름';   -- 기한 늘리기
update economy.ops_keys set revoked_at = now() where label = '담당자 이름';   -- 막기(열린 세션도 바로 끝난다)
```

- **아이템 지급**: 누구에게(이메일 — 붙여 넣기 · 이름으로 찾기 / 최근 7일 달린 사람 / 전체) → 무엇을 → 몇 개(1 ~ 99) → 사유 → 푸시 여부 → 확인.
  가입하지 않은 이메일은 빼고 지급하고 화면에 알려 준다. 응답을 잃고 다시 눌러도 한 번만 지급된다(요청 번호).
  요청 번호는 **보낸 내용**(받는 사람 · 종류 · 개수 · 사유 · 푸시)에 묶는다 — 답을 못 받았으면(끊김 · 5xx) 기록 탭을 다녀오거나
  화면이 다시 그려져도 같은 내용이면 같은 번호로 다시 보낸다. 내용이 달라지거나 서버가 분명히 답하면 새 번호(2026-11-17 점검 —
  예전에는 화면을 다시 그리기만 해도 번호가 바뀌어 "다시 눌러 주세요"가 두 번 지급이 될 수 있었다). 이벤트 시작도 같다.
- **보상 이벤트**: 이름 · 배수(1 초과 ~ 5) · 기간(1 ~ 168시간) · 지금 / 예약. 그 시간에 **시작한** 러닝의 적립 × 배수(모든 사람).
  겹치는 이벤트는 만들지 못한다. 끄면 그때부터 꺼진다. 지금 시작하는 이벤트만 시작 푸시가 간다(예약은 안 간다).
- **기록**: 최근 지급(되돌리기 — 아직 갖고 있는 만큼만 거둔다) · 이벤트 기록 · 아이템 현황(가진 사람 · 개수 · 쓴 수).
- 지급 · 되돌리기 · 이벤트는 `public.admin_audit` 에 남는다(`detail->>'by'` = 키 이름).

## 운영자 페이지 보안 (2026-11-18, 서버 0114)

사용자 "운영자 페이지 보안 더" — 방법은 맡겼다. 예전(0106)에는 키 하나를 모든 요청에 실어 보냈고, 그 키를 가진 사람은 누구에게나 아이템을 줄 수 있었다.
이제 서버가 아래 다섯 겹을 지키고(`supabase/migrations/0114_ops_security.sql`), 가장 바깥 겹(Cloudflare Access)은 사용자가 대시보드에서 켠다.

| 겹 | 하는 일 | 바꾸는 값(`economy_settings`) |
|---|---|---|
| 세션 | `ops_login(키)` → 무작위 세션 번호(서버에는 해시만). 8시간까지 · 30분 쓰지 않으면 끝(쓸 때마다 다시 30분). `ops_logout`. 다른 운영자 함수는 **세션 번호만** 받는다(키를 그대로 보내면 거절) | `ops_session_hours` 8 · `ops_session_idle_min` 30 |
| 키 기한 | 키마다 `expires_at`(기본 30일). 기한이 지나거나 막은 키는 로그인도, 열려 있던 세션도 바로 끝 | `ops_key_new(이름, 날 수)` |
| 로그인 잠금 | 같은 곳(IP — 서버만 아는 소금 친 해시, 원문은 어디에도 남기지 않는다)에서 10분에 5번 틀리면 그곳 15분, 모든 곳 합쳐 10분에 30번이면 **모든 로그인** 15분. 막힌 동안의 시도는 키를 보지도 쌓지도 않는다 | `ops_login_client_fails` 5 · `ops_login_global_fails` 30 · `ops_login_window_min` 10 · `ops_login_lock_min` 15 |
| 큰 일 다시 확인 | 전체 지급 · 200명 넘는 지급 · 3배 이상이거나 48시간 넘는 이벤트 · 지급 되돌리기는 그 요청에 키를 한 번 더(`p_confirm`) — **이 세션을 연 키**여야 한다. 틀리면 로그인 실패로 세고, 한 세션에서 세 번 틀리면 그 세션은 끝. 요청 번호(같은 일은 한 번만)는 그대로 | `ops_confirm_recipients` 200 · `ops_confirm_mult` 3 · `ops_confirm_hours` 48 |
| 하루 지급 한도 | 키마다 한국 날짜 하루 아이템 5,000개(받는 사람 수 × 개수)까지 — 넘는 지급은 통째로 거절, 남은 수를 알려 준다. 되돌려도 한도는 돌아오지 않는다 | `ops_key_daily_units` 5000 |

- 값 바꾸기: `select admin_economy_set('ops_key_daily_units', '20000');` — 가입자가 5,000명을 넘으면 전체 지급 전에 한도를 올린다.
- 거절은 `{ok:false, code, message}` 로 답한다(`wrong` · `expired` · `locked` · `confirm_required` · `confirm_wrong` · `confirm_locked` · `cap`) — 예외로 답하면
  실패 기록까지 되돌려 잠금이 세지 못한다(0082 대기 명단과 같은 까닭). 끝난 세션만 예외(42501 → 401)다. 55000 · P0002 는 쓰지 않는다.
- 감사 기록(`public.admin_audit`, 키 · 세션 번호 · IP 없이): `ops_login` · `ops_login_fail`(까닭 · 곳 해시 앞 12자) · `ops_login_locked` · `ops_logout` ·
  `ops_confirm_fail` · `ops_grant_cap`, 지급 · 이벤트에는 `confirmed`. 보안 감시(`security-watch.yml`, 한 시간마다)의 "운영자 함수 사용"에 그대로 보인다 —
  모르는 로그인 · 잠금이 보이면 키를 막는다.
- 손으로 풀기 · 끝내기(SQL Editor): 잠금 풀기 `delete from economy.ops_login_locks;` · 모든 세션 끝내기
  `update economy.ops_sessions set ended_at = now(), ended_why = 'manual' where ended_at is null;`
- 페이지(`web/ops/`): 로그인 → 세션 번호만 탭에(예전 페이지가 남긴 키는 지운다) · 위에 로그인 · 키 기한(7일 안이면 노란 글) · 로그아웃.
  큰 일은 확인창 대신 키 입력창 하나, 서버가 뒤늦게 키를 요구하거나 틀렸다고 하면 같은 창에서 다시 묻고 같은 요청 번호로 다시 보낸다.
  지급 칸 아래 오늘 남은 한도. 30분 쉬거나 8시간이 지나면 화면도 로그인으로 돌아간다(서버와 같은 기준).

### 가장 센 겹 — Cloudflare Access (사용자가 대시보드에서, 무료)

`stepupcrew.com/ops*` 앞에 Cloudflare 로그인을 세워, 명단에 있는 이메일로 받은 코드를 넣은 사람만 페이지를 열게 한다. 키가 새도 페이지를 찾거나 쓰지 못한다.

1. dash.cloudflare.com → 왼쪽 **Zero Trust**. 처음이면 팀 이름(예: `stepup`)과 **Free** 요금제(50명까지 0원 — 결제 수단을 물을 수 있지만 청구되지 않는다)를 고른다.
2. **Settings › Authentication › Login methods** — **One-time PIN**(이메일로 받는 코드)이 기본으로 있다. 원하면 Google 을 더한다.
3. **Access › Applications › Add an application › Self-hosted**
   - Application name `StepUp 운영자` · Session duration `8 hours`(서버 세션과 같게).
   - 주소(Public hostname / Application domain): Subdomain 비움 · Domain `stepupcrew.com` · Path `ops`.
   - **같은 앱에 Pages 주소도 더한다**(Add public hostname): Workers & Pages › 이 사이트 프로젝트에 보이는 `<프로젝트>.pages.dev` · Path `ops`,
     미리보기 주소 `*.<프로젝트>.pages.dev` · Path `ops`. 빼면 그 주소로 들어와 Access 를 건너뛴다.
4. **Policies › Add a policy** — 이름 `운영자`, Action **Allow**, Include **Emails** 에 운영자 이메일을 하나씩(“Emails ending in” 은 쓰지 않는다 — `gmail.com` 전체가 열린다).
5. 저장한 뒤 시크릿 창으로 `https://stepupcrew.com/ops/` 와 `https://stepupcrew.com/ops/ops.js` — 둘 다 Cloudflare 이메일 코드 화면이 먼저 나와야 한다.
   명단에 없는 이메일로도 해 보고 막히는지 본다. `<프로젝트>.pages.dev/ops/` 도 같은지 본다.
6. 사람이 바뀌면 정책의 이메일만 고친다. 누가 들어왔는지는 Zero Trust › Logs › Access 에 남는다.

**한계**: Access 는 페이지(HTML · 스크립트)를 가린다. 서버 함수(`ops_login` 등)는 Supabase 주소로 바로 부를 수 있어 Access 를 거치지 않는다 —
키를 가진 사람이 페이지 없이 부르면 위 다섯 겹(세션 · 기한 · 잠금 · 다시 확인 · 한도)만 남는다. 이것까지 막으려면(코드 일, 아직 안 함)
로그인을 Access 뒤의 Pages Function(`/ops/api/login`)으로 옮겨 Access 가 붙이는 `Cf-Access-Jwt-Assertion` 을 확인하고, `ops_login` 은 그 함수만 아는
비밀이 함께 와야 세션을 주게 한다 — 그러면 Access 를 통과하지 않은 키는 쓸모가 없다.

    출발을 그만둘 때(권한 안내 · 위치 안내 닫기 · 3-2-1 취소 · 시작 거절)마다 비운다(`clearPicks`). 점검 없이 켜지는 러닝(크루 · 번개 대기실
    출발, 챌린지 · 코스 · 다이어트)에는 쓰지 않는다 — 2026-11-17 점검: 예전에는 고르다 만 아이템이 10분 안에 시작한 크루 러닝에 쓰였고,
    점검을 10분 넘게 열어 두면 "출발하면 고른 아이템을 써요"라고 하고는 쓰지 않았다.
  - 보상 이벤트 · 24시간 부스터가 이미 켜져 있으면 그보다 **크지 않은 배수 아이템은 고르지 못한다**(흐리게 + 한 줄 안내 — `RunItemPicks.covered`).
    서버는 큰 것 하나만 쓰므로 고르면 아이템만 사라졌다. 에너지 드링크는 그대로 고른다.
  - 폰 시계가 앞서 서버가 시작 시각을 받지 않으면("러닝 시작 시각이 올바르지 않습니다") 버리지 않고 러닝과 함께 다시 보낸다(하루 안의 러닝만).
    그 밖의 거절은 버리고 가방을 다시 읽어 미리 뺀 개수를 되돌린다.
  - 로그아웃 · 계정 지우기 때 가방 사본 · 고른 것을 비운다(`ItemsRepository.clear` — `forgetAccountOnPhone`).
