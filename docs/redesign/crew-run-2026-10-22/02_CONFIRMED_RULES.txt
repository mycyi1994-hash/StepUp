StepUp 크루 러닝 — 확정 규칙
원본: 사용자가 제공한 2026-10-21 작업 정의서 + 문자 발송 제외 지시.
이 문서는 제품 규칙이다. RPC/테이블 이름 등 구현 제안과 구분한다.

R01. 오늘 크루 체력: 하나의 공용 내구도
• 범위는 crew_id + 한국 날짜. 방별 풀, 사용자별 몫, 에너지/걸음 나눠쓰기 모델이 아니다.
• 오늘 크루 러닝에 참가하며 고른 신발들의 '최대 내구도 합' × (1 + 크루 레벨 체력 보너스).
• 해당 참가자가 실제로 출발할 때 그 사람의 선택 신발 최대 내구도가 기여한다. 대기실 입장·신발 선택·준비만으로 더하지 않는다.
• 남은 개인 내구도가 75/100이면 최대값 100을 사용한다. Lv7이면 100×1.36=136을 더하는 예시다.
• 매일 00:00 한국 시간에 일일 풀은 비워진다. 수리 기능은 없다. 일일 풀 기록과 과거 정산 이력은 보존한다.
• 여러 대기실이 동시에 같은 크루에서 러닝하더라도 하나의 공용 풀이다.
• 0/0은 아직 기여가 없는 새 하루, 0/816은 만들어진 체력을 모두 사용한 상태다. 둘 다 단순히 '참여 불가'로 해석하지 않는다. 새로운 참가자는 출발할 때 기여할 수 있다.

R02. 사용량과 개인 신발 보호
• 러닝 중인 각 사람마다 공용 내구도 5/분 사용.
• 동시에 6명이 달리면 30/분, 20명이 달리면 100/분 사용한다.
• 일시정지한 사람은 자신의 러닝/적립/체력 사용이 멈춘다. 다른 사람이 달리면 공용 바는 계속 줄어든다.
• 크루 러닝은 개인 신발 내구도를 차감하지 않는다. 자유 러닝은 기존 개인 신발 내구도 사용 방식으로 별도 가능하다.
• UI의 초·분 표기와 서버 내부 소수 정밀도를 구분한다. 초 단위 비례 차감은 구현 권장안이며 최소 과금 단위·반올림은 07의 결정 항목을 확인한다.

R03. 체력 0
• 0이 된 시점부터 이후 걸음에 대한 적립을 멈춘다.
• GPS 경로, 거리, 시간 등 러닝 기록은 계속된다. 0만으로 세션을 강제 종료하지 않는다.
• 개인 신발로 전환하거나 개인 내구도를 대신 차감하지 않는다.
• 전부 끝난 후 개인 신발이 닳았다는 결과 문구를 쓰지 않는다.
• 20% 도달 알림은 화면 요구사항이다. 같은 소진 구간에서 반복 알림이 쏟아지지 않도록 처리한다.
• 다른 신규 참가자의 기여로 0에서 다시 체력이 생긴 경우의 적립 재개 방식은 원문에 명시되지 않았다. 07 참조.

R04. 개인별 보상
• 기본 보상은 본인이 출발 때 선택한 신발의 효율·착화감·기타 기존 보상 속성으로 계산한다.
• 참가자의 능력치를 평균내거나 합친 보상을 N분의 1로 나누지 않는다.
• 기존 서버의 유효 걸음·속도·신발 보상 공식을 재사용한다. 이 시안에는 기본 보상 공식을 새로 정의하지 않았다.
• 공용 체력이 보상을 허용한 유효 구간의 기본 보상 B에 인원/레벨 보상을 적용한다.

R05. 하루 한 번
• 사용자 계정 전체 기준 하루 1회, Asia/Seoul 날짜 경계.
• 같은 날 크루를 바꾸어도 참여권이 생기지 않는다. 방을 바꾸어도 같다.
• 대기실 입장·준비·출발 확인 열기는 사용이 아니다. 실제 출발이 서버에서 확정될 때 일일 참여권과 기여를 같은 트랜잭션으로 기록한다.
• 시작 응답 유실·연타·재접속으로 같은 세션을 복구하는 것은 새 참여가 아니다. 기여·횟수도 중복되지 않는다.
• 끝내기를 확정하면 그날 크루 러닝 종료, 다시 들어올 수 없다.

R06. 러닝 수명과 종료
• 일시정지와 재개 가능. 재개는 같은 run_id를 사용한다.
• 다른 참가자가 모두 종료하여 혼자 남으면 마지막 참가자도 크루 러닝 자동 종료.
• '혼자 남음'은 세션 참가 상태 기준이다. 인증된 보너스 인원이 1명이라는 이유로 종료하지 않는다.
• 잠시 쉬는 참가자, 앱 백그라운드 참가자, 네트워크 연결이 끊긴 참가자를 바로 '끝냄'으로 간주하지 않는다. 연결 시간 만료 정책은 별도 확인한다.
• 진행자가 자신의 러닝을 끝내는 것과 방 전체 강제 종료를 섞지 않는다. 기존 host 종료 정책이 다르면 새 규칙과의 충돌을 해결한다.

R07. 보너스 인원 판정
다음 조건을 모두 만족하는 사람을 집계한다.
1) 그 크루의 크루원이다.
2) 같은 대기실에서 500m 안에 모여 함께 출발했다.
3) 출발 2분 뒤에도 500m 안에 있다.
4) 휴대폰 번호 인증 상태가 신뢰할 수 있는 서버 자료로 확인된다.
• 대기실 보너스는 예상치. 2분 확인 전에는 확정 보너스나 적립 완료로 표현하지 않는다.
• 500m 기준점, 위치 샘플 허용 시간/정확도, 첫 2분 보상의 처리 방식은 미정이다.
• 준비 인원, 실제 출발 인원, 현재 달리는 인원, 보너스 집계 인원, 오늘 크루 전체 참가 인원은 서로 다른 값이다.
• 보너스 인원이 0~1명인 경우 확정 표에 인원 가산은 없으므로 +0%로 표기하되, 물리적으로 여러 명이 참가한 러닝을 미인증 때문에 막지 않는다.

R08. 인원 보너스 — 구간 중복 없음
2명 +5%   / 3명 +10%  / 4명 +15%  / 5명 +20%
6명 +50%  / 7명 +52%  / 8명 +54%  / 9명 +56%
10명 +58% / 11명 +60% / 12명 +62% / 13명 +64%
14명 +66% / 15명 +68% / 16명 +70% / 17명 +72%
18명 +74% / 19명 +76% / 20명 +150%
7~19명 = 50% + (인원−6)×2%.
예: 6명 보너스는 +50%다. 2~5명 구간을 누적해서 +100%로 만들지 않는다.

R09. 크루 레벨과 경험치
• Lv1~Lv20. 경험치는 유효한 크루 러닝의 누적 거리다.
• 같이 뛴 각 사람이 자기 거리를 기여한다. 6명이 각 3km면 총 18km다. 방 경로 길이 3km 한 번만 더하는 방식이 아니다.
• 무효 러닝 제외. 같은 run_id 재저장·재시도로 경험치 중복 적립 금지.
• 레벨은 내려가지 않는다. 이미 오른 레벨의 재검증/무효화 후 하향 조정 금지. 원장의 정정 절차는 별도 설계한다.
• 일일 자정 초기화는 누적 거리나 레벨을 지우지 않는다.

R10. 레벨과 인원 보너스 결합
체력 보너스 = 0.06 × (Lv−1)
크루 보상 레벨 보너스 = 0.01 × (Lv−1)
총 보상 = B × (1 + 인원 보너스 + 레벨 보너스)
Lv1을 +6%/+1%로 시작하지 않는다.
20명 Lv20 = +150% +19% = +169%, 즉 기본 보상의 2.69배.
6명 Lv7, B=48 SUP → 48 +24 +2.88 =74.88 SUP.
1.50×1.06 같은 곱셈, 또는 20명에서 2.50×1.19 곱셈은 사용하지 않는다.

R11. 상한
• 개인 하루 상한 600 SUP와 크루 러닝 보상은 별도다.
• 현재 크루 러닝 보상 하루 상한은 무제한. 공용 내구도가 실제 적립 가능 범위를 제한한다.
• 임의의 600 상한, 에너지 상한, 개인 몫 상한을 크루 보상에 적용하지 않는다.
• 경제 영향은 출시 후 수치로 조정할 열린 질문이다. 이번 구현에서 임의의 상한을 추가하지 않는다.

R12. 인증과 문자 제외
• 번호 하나 = 계정 하나라는 중복 방지 원칙 유지.
• 미인증자도 참가·공용 체력 기여·자기 신발 기준 보상 가능. 인원 보너스 인원에서만 제외.
• 이미 있는 서버 인증 상태를 읽는다. 신규 문자 발송, 인증업체, OTP·번호 입력·설정 인증 UI는 만들지 않는다.
• 검증된 번호 식별자가 기존 시스템에 있으면 계정 중복을 서버에서 막는다. 없다면 클라이언트가 번호를 수집하거나 임의로 인증시켜 대신하지 않는다.

R13. 대기실
• 크루원 누구나 대기실 생성 가능. 크루장 전용 아님.
• 최대 20명. 크루 전체 정원과 방 정원을 혼동하지 않는다(시안의 크루 정원 30은 예시다).
• 시작 직전에 실제 크루 소속, 세션 참여 가능 여부, 거리, 선택 신발 소유를 서버가 다시 확인한다.
• 출발 전 미인증 또는 공용 체력 0만으로 출발 불가 처리하지 않는다.

통합 예시
기존 오늘 풀 612/816. 새 참가자 6명 × 최대 내구도100 × Lv7 1.36 =816 추가.
출발 직후 1,428/1,632. 6명이 모두 21분20초 달린 예시 사용량 =640, 잔여788/1,632.
개인 사용량은 106.666…을 화면에서106.7로 표시한 예시이며, 자신의 지분/한도가 아니다.
각자의 기본 보상은 서로 다를 수 있다. 예시의 내 기본 보상48은 서버 정산 예시값이지 '분당 SUP 공식'이 아니다.
