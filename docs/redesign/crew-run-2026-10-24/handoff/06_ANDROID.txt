Android / Compose 통합 지시

1. 먼저 확인할 실제 코드
과거 참조 이름: CrewLobby.kt, CrewRunScreens.kt, CrewHomeScreen.kt, CourseHubScreen.kt, CrewRunKit, CrewRunLive, CrewBlueKit, CrewStaminaParts.
정확한 현재 경로·API·화면 클래스는 저장소에서 찾아라. 이 패키지가 최신 저장소 클래스의 존재를 보증하지 않는다.
기존 디자인 시스템, Navigation, ViewModel, Supabase repository, GPS/Foreground Service, 신발 인벤토리, 지도·결과·공유 서비스를 재사용한다.
기존 화면을 모두 새 화면으로 복제하거나, 70개 독립 Activity/route를 만들지 않는다.

2. 권장 화면군
CrewHome / RoomList / RoomCreate / CoursePicker + CourseDetail
CrewLobby + 역할/준비/인원 상태
CrewRun + 기록·일시정지·내구도·보너스 상태
CrewRunResult + 저장/정산 상태
Level / History
공통 시트: ShoePicker, Roster, PoolDetail, LevelDetail, BonusTable, Rules, StartConfirm, EndConfirm, Notice.
실제 명칭은 현재 프로젝트에 맞춘다.

3. 상태 모델 경계
상태는 최신 서버 스냅샷과 로컬 UI 선택/진행 요청을 분리한다.
CrewOwnerRole과 LobbyHostRole을 별도 값으로 둔다. UI 숨김만으로 권한을 보장하지 말고 서버도 검증한다.
실제 참가 수, 준비 수, 현재 뛰는 수, 미종료 수, 보너스 유효 인원 수를 하나의 count로 합치지 않는다.
RunPhase: 대기/준비/출발 요청/러닝/휴식/종료 처리/종료.
BonusState: 확인 전/확정/지연 또는 확인 불가. 휴식 여부와 별개.
EarningState: 적립 가능/정산 대기/공용 풀 소진/휴식. 러닝 기록 여부와 별개.
SaveState: 미저장/저장 중/재시도 필요/정산 확인/무효 판정.
풀 total/remaining/null, canParticipate/usedToday, selectedShoe/draftShoe를 별개로 둔다.
UI는 상태 간 모든 조합을 별도 스크린으로 복제하지 않고 공통 컴포넌트에 매핑한다.

4. 대기실과 코스
모든 멤버는 명단·공용 내구도·목표·코스와 자기 신발을 본다.
진행자만 코스를 편집하고 출발을 확정한다. 크루 소유자만 방을 만들 수 있도록 제한하지 않는다.
코스 목록 → 상세 → 선택 확정으로 이어져야 한다. 목록에서 스치거나 Back으로 나왔다고 적용하지 않는다.
코스 변경은 방의 course_id/version으로 전파한다. 참가자는 경로 변경 알림과 읽기 전용 상세를 본다.
변경 후 준비 해제 여부는 기존 정책부터 확인한다. 준비된 인원의 출발 직전 코스 버전 불일치는 서버에서 막는다.
선택 신발도 임시 선택과 확정을 분리한다. 취소하면 기존 선택을 유지한다. 출발 요청 직전 소유권·가능 상태를 재검증한다.
부분 출발은 확정된 준비 인원과 서버 승인 인원을 기준으로 한다. 5명 출발인데 6명 보너스를 사용하지 않는다.
내보내기는 선택한 user_id 한 명을 대상으로 한다. 표시 이름만으로 처리하지 않고 화면/목록/ready count를 서버에서 갱신한다.

5. 연결과 복구
출발 버튼 연타/네트워크 타임아웃에서 중복 run 또는 기여가 생기지 않는다. 같은 요청 키로 상태 조회/재시도한다.
출발 서버 성공 전에 로컬 카운트다운으로 새 러닝을 독립 생성하지 않는다.
GPS와 2분 판정은 실제 위치 업로드/서버 상태를 기다린다. 시안의 클릭 이동·타이머 성공을 복제하지 않는다.
실행 중 프로세스가 사라져도 기존 run_id, 선택 신발 스냅샷, 서버 종료 상태를 복구한다.
일시정지 동안 내 소모·내 기록의 휴식 처리 규칙을 유지하고 공용 풀 구독은 계속한다.
공용 풀 0 상태에서 휴식 후 재개해도 적립 가능으로 임의 복원하지 않는다. 서버가 인정한 적립 상태만 반영한다.
마지막 참가자 자동 종료 알림의 X/Back은 종료를 취소하지 않는다. 이미 terminal 상태인 세션을 다시 달리는 상태로 만들지 않는다.
러닝 화면의 Back/알림 탭/지도 보기/시트 닫기는 기록 서비스나 세션을 종료하지 않는다.
오프라인 기록은 현재 앱의 영속 저장 경로에 보관한다. 로컬 기록 저장과 SUP 지급 완료를 혼동하지 않는다.

6. 실제 알림과 공유
모집·레벨 업 푸시는 기존 구현이 있는지 확인한다. 이번 요구의 푸시는 선택 기능이며 문자 발송과 다르다.
모집 알림 전송 성공은 실제 응답으로 표시한다. 눌렀다고 1.6초 후 성공으로 바꾸지 않는다.
GPS 러닝 서비스의 실제 ongoing notification에 공용 내구도·적립 상태·동일 run 복귀 동작을 연결한다.
잠금화면 시안의 시계·날짜·시스템 프레임을 앱 콘텐츠로 구현하지 않는다.
공유는 실제 결과 데이터와 기존 공유 서비스/Android 공유 동작을 재사용한다. 시안은 공유 미리보기만 보여준다.

7. 결과와 오래된 기록
저장 시도와 보상 정산을 분리한다. 정산 미완료면 Pending, 실패면 재시도 상태로 표시한다.
결과의 거리·시간·선택 신발·인원·레벨·보너스·원장은 동일 run_id의 서버 결과여야 한다.
내 신발 기본 보상/인원 추가분/레벨 추가분/최종 합계가 실제 정산 수치와 일치해야 한다.
당시 레벨과 인원 스냅샷을 보존하고 오늘 크루 레벨로 과거 보상을 재계산하지 않는다.
내구도 '나의 기여', '내 소모', '이번 방의 소모', '전체 크루 잔량/총량'을 혼동하지 않는다.
기록 조회/공유/화면 재진입이 다시 XP나 보상을 지급하지 않는다.
Lv.20에서는 다음 Lv.21/남은 음수 km를 표시하지 않고 만렙 상태를 사용한다.
무효 러닝의 보상·체력 환급·참여권 복구는 미정이므로 서버 사유와 확정 정책을 따른다.

8. 완료 순서
확정 규칙 표/순수 계산과 서버 계약 → 공유 UI 부품/대기실 → 코스·준비·출발 → 기록/풀 차감/2분 확인 → 결과·복구 → 실제 기기 검증.
UI를 먼저 볼 수 있게 mock repository 또는 Compose preview fixture를 둘 수 있지만 운영 데이터 공급자와 분리한다.
프로토타입 파일은 시각 자료다. window.openai, 갤러리 셀렉터, 고정 상태바·시간, 샘플 참가자 배열, setTimeout 저장 성공을 제품에 넣지 않는다.
참조 화면 ID와 실제 route/composable/state의 대응표를 마지막에 작성한다.
