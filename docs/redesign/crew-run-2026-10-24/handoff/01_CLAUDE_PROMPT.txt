아래 지시와 첨부 StepUp 핸드오프를 기준으로 실제 앱 구현을 진행해.

목표
StepUp Android(Kotlin / Jetpack Compose)와 Supabase(Postgres / RPC)의 크루 러닝을 새 공용 내구도 규칙으로 개편한다. 현재 앱의 실제 화면과 서버 코드에 통합해야 한다. HTML을 WebView에 띄우는 방식으로 대체하지 마.

최우선: 내가 승인한 디자인을 바꾸지 마
선택한 디자인은 3번 듀얼 레일이다. 크루원과 내 신발 영역의 아이스 블루 5dp 외곽 프레임, 안쪽 두 번째 선, 짙은 남색 내부, 흰 주요 버튼을 유지해.
최신 변경: 사진 기반 터널 애니메이션은 대기실에만 적용해. 크루 홈, 개설, 코스 선택, 러닝 중, 결과, 레벨 화면에는 현재 앱의 기존 배경을 사용해. 지도 화면은 실제 지도 중심으로 구현해.
첨부 원본 시안은 다시 만들지 않았기 때문에 다른 장면에도 터널이 보인다. 이것은 배경 적용 지시가 아니다. 04_DESIGN_BACKGROUND.txt와 screen-spec.json의 backgroundPolicy가 이미지보다 우선한다.
대기실 위에 뜬 시트는 부모 배경을 어둡게 가리고 움직임을 멈춘다. 시트 자체는 불투명한 기존 앱 표면이다.

1. 저장소의 AGENTS.md / CLAUDE.md, 디자인 시스템, 내비게이션, 실제 크루/러닝 화면과 신발·지도·서체 리소스를 읽어.

3. 실제 바꿀 파일, 재사용할 부품, 서버 계약 변경을 짧게 정리한 뒤 구현을 계속해. 계획만 쓰고 끝내지 마.
4. 이미 구현된 새 규칙은 다시 만들지 말고 차이를 수정해. 미정 정책은 기존 구현에서 먼저 답을 찾고, 없으면 영향과 선택지를 모아 보고해. 확정된 나머지 작업은 계속해.

반드시 지킬 규칙
• 공용 내구도는 같은 크루·같은 한국 날짜에 하나다. 방별 풀, 개인에게 나눠 주는 에너지 몫이 아니다.
• 실제 출발 시 선택 신발의 최대 내구도 × [1 + 0.06 × (레벨−1)]를 한 번 더한다. 현재 남은 개인 내구도를 곱하지 마.
• 매일 한국 시간 00:00에 오늘 풀은 비워진다. 수리 없음. 과거 원장은 보존한다.
• 뛰는 사람마다 분당 5만 공용 풀에서 차감한다. 개인 신발은 닳지 않으며 휴식자의 소비는 0이다.
• 공용 풀이 0이 된 구간은 적립하지 않는다. 기록은 계속한다. 개인 신발로 전환하지 않는다.
• 보상은 각자의 선택 신발 기본 보상 × (1 + 인원 보너스 + 레벨 보너스)다. 평균 내거나 두 보너스를 서로 곱하지 마.
• 한 사람의 크루 러닝 출발은 한국 날짜별 하루 1번. 다른 방·다른 크루로 옮겨도 동일하다. 준비/방 생성은 출발이 아니다.
• 일시정지는 가능하다. 끝내기 후 그날 재입장 불가. 다른 사람이 모두 종료해 마지막 1명이 남으면 그 사람도 서버에서 종료한다.
• 크루원 누구나 방을 열 수 있다. 최대 20명. 크루 소유자와 대기실 진행자를 별개로 다뤄.
• 인원 보너스는 같은 크루·같은 방, 출발과 120초 뒤 모두 500m 조건, 신뢰된 번호 인증을 충족한 인원만 센다.
• 번호 미인증 사용자도 참여·자기 신발 보상·풀 기여가 가능하다. 인원 수에서만 제외한다. SMS/OTP는 만들지 마.
• 인원 보너스: 2~5명 5/10/15/20%, 6명 50%, 7~19명 52~76%로 1명당 2%p, 20명 150%. 구간 하나만 적용한다.
• 레벨 1~20, 체력은 (Lv−1)×6%, 보상은 (Lv−1)×1%. 20명·Lv20은 총 +169%, 보상 2.69배다.
• XP는 유효한 개인별 크루 러닝 거리의 합. 중복 적용·무효 거리 반영·레벨 하락 없음.
• 크루 보상은 개인 600 SUP 한도와 별도이며 현재 일일 상한을 두지 않는다.
전체 임계값과 경계 조건은 02_RULES.txt / rules.json을 따라.

화면 구현
03_SCREEN_BEHAVIOR.txt의 70개 ID를 화면/시트/상태 단위로 빠짐없이 대응시켜.
진행자: 개설 → 코스 목록 → 상세 확인 → 대기실 → 코스 변경/참가자 관리/모집 → 출발 확인.
참가자: 대기실 → 내 신발 선택 → 준비 완료/취소 → 진행자 출발 대기.
출발: 서버 start 성공·출발 시각을 받은 뒤 3→2→1→0→StepUP!→중앙에서 지도와 러닝 화면이 열리는 연속 전환. 0에서 로고가 나올 때 빈 프레임·재마운트 끊김이 없어야 해.
러닝: 2분 확인 중/확정/부분 제외/확인 지연, 휴식, 공용 풀 20%·0, 끝내기, 마지막 참가자 종료, 잠금화면.
결과: 저장 중/실패/정산 확인, 자기 신발+인원+레벨 보상, 기여 거리, 공용 소모, 레벨 업, 기록과 공유.
예외: 이미 참여, 크루 이동, GPS/권한, 네트워크/재연결, 무효, 자정, 불러오기 실패, 내보내짐.
대기실은 짧게 유지해. 자세한 규칙·보너스 표·내구도 산식은 시트로 보내고 한 화면의 주 행동은 하나로 둬.

서버와 앱의 경계
핸드오프의 테이블/RPC 이름은 논리 제안이다. 기존 구조를 먼저 재사용해.
출발·기여·진행 차감·보상·거리·레벨 이벤트에 멱등성을 적용하고 동시에 여러 방이 같은 풀을 쓰는 경합을 처리해.
종료 때 record_session 한 번만 처리하는 방식으로는 실시간 풀 0 경계를 보장할 수 없다. 현재 progress/heartbeat/기록 서비스를 확인해서 중간 정산과 소진 시각을 연결해.
서버가 판정한 확정값을 사용해. 클라이언트가 인원·검증 여부·보상·레벨·내구도를 직접 결정하게 만들지 마.
신규 migration 번호는 실제 이력 확인 후 정해. 이미 적용된 파일을 덮어쓰거나 개인 러닝 경제 경로를 바꾸지 마.

실제 위치·신발 소유·러닝 기록·보상 원장·서버 상태를 쓰고 기존 앱의 실제 권한/알림/공유 동작에 연결해.
