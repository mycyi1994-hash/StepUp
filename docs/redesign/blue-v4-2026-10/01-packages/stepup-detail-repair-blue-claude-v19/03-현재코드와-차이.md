# 현재 코드와 필요한 변경

확인 대상은 stepup-waitlist-implementation이다. 이 작업에서는 소스를 읽어 시안과 구현 경계를 정리했으며 앱 코드를 변경하거나 실행하지 않았다. 전달받은 저장소의 최신 상태를 먼저 확인한다.

| 확인된 현재 상태 | 이번 디자인에 필요한 변경 |
|---|---|
| SneakerDetailScreen의 DetailSheet가 Stats와 Explain 및 Info를 분리한다 | 본문을 네 독립 바에 통합하고 기록 모달은 관리에서 연다. 낡은 속성·행운 화면을 다시 메인으로 노출하지 않는다 |
| 관리 메뉴에서 onEnhance를 호출한다 | 상세 하단의 직접 강화 버튼을 별도 강화 페이지에 연결한다 |
| 관리의 onRepair는 시트를 닫고 곧바로 ViewModel.repair를 호출한다 | 수리 정보 조회와 명시적 비용 확인 모달을 먼저 추가한다 |
| ItemsViewModel.repair는 결과를 Repaired 또는 일반 메시지로 보낸다 | 대상 ID에 묶인 조회·확인·진행·결과 미확인·완료 표시 상태와 중복 요청 방지가 필요하다 |
| EconomyApi.repair는 sneaker_repair에 p_id만 보낸다 | 현재 견적 토큰·금액 상한·요청 ID·요청별 상태 조회 계약은 없다. 이를 이미 존재하는 API처럼 호출하지 않는다 |
| Repository는 Ok 또는 Offline 후 재동기화한다 | 재동기화를 실제 작업 결과 확정과 동일시하지 않는다. 성공 표시 전에 대상 값과 잔액 동기화를 확인한다 |
| Rarity 기본 상한은10/15/20/30이며 서버의 양수 maxLevel이 우선한다 | 최신 사용자 정책은 최대20이다. 서버 정책과 기존 데이터 전환까지 함께 맞추기 전 UI 분모만20으로 고정하지 않는다 |
| 수리 메뉴 노출 조건에 server.upgradable가 사용된다 | 강화 가능과 수리 가능은 같은 정책이라고 가정하지 않는다. 서버의 소유·APP상태·판매상태·내구도로 실제 가능 여부를 대조한다 |

## 레벨 상한

이 시안의5/20은 최신 사용자 정책을 보여주는 예시다. 현재 서버와 데이터가 이미 최대20 정책이라는 뜻이 아니다. 실제 배포는 상세·강화·서버 응답을 같은 정책으로 맞춘 뒤 적용한다. 기존에20을 넘는 소유 신발이 있다면 클라이언트에서 값을 낮추거나 잘라 저장하지 않는다. 전환 정책이 미정인 데이터는 실제 값을 보존하고 미해결 항목으로 보고한다.

## 착용 결과

현재 classifyEquip는 저장된 wearing ID가 대상 ID와 같을 때만 Worn으로 분류한다. 이 원칙을 유지한다. REJECTED와 SIGN_IN은 확정 거절, OFFLINE과 UNCONFIRMED는 결과 미확인이다. 기존 오류 UI의 다시 신기를 미확인 결과에 그대로 연결하지 않는다. 미확인 상태에서는 먼저 실제 착용을 조회한다.

확정 거절 문구는 조회된 기존 착용 신발 이름으로 쓴다. 기존 착용이 없으면 계속 신고 있어요라고 말하지 않는다. 세션 복귀 뒤 자동으로 착용 요청을 보내지 않는다. 대상이 성공 조회한 보유 목록에서 사라진 경우에는 없는 신발 화면으로 이동한다.

## 수리 결과와 비용 변경

현재 RPC는 서버 내부에서 현재 신발 상태로 비용을 다시 계산하고 차감한다. 클라이언트에서 직전에 조회하는 것만으로 확인한 가격과 실제 차감액의 일치를 보장할 수 없다. 비용이 바뀌면 새 금액을 보여주는 RP10은 이 변경을 감지한 경우의 UI다. 동시 변경까지 보장하려면 서버의 버전 또는 견적·최대금액 검증 계약이 추가로 필요하다. 문서가 그 기능의 구현 완료 증거는 아니다.

중복 수리는 클라이언트에서 즉시 막는다. 앱 재시작 후에도 대상과 진행 중 요청을 복구할 필요가 있지만, 현재 서버에는 요청 ID를 통한 멱등 처리나 결과 조회가 없다. 단순히 HTTP 호출을 다시 보내서 복구했다고 하지 않는다. 서버 응답을 못 받은 뒤 내구도·잔액만으로 어느 작업이 적용됐는지 확정할 수 없다면 미확인 상태를 유지한다. 요청별 결과 계약을 구현하거나 신뢰할 수 있는 서버 작업 기록과 연결하는 것은 추가 구현 사항이다.

RP04의 사용 금액과 남은 잔액은 확정된 작업과 동기화된 장부 값이 필요하다. 단순히 현재 내구도가100이라는 이유만으로 내가 보낸 수리가 성공했다고 판단하지 않는다. 확인 중 버튼의 조회가 실패해도 재차 차감 요청을 보내지 않는다.
