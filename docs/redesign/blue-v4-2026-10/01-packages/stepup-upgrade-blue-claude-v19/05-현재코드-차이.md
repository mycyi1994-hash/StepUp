# 현재 코드와 새 강화의 차이

2026-10-03 로컬 stepup-waitlist-implementation을 읽어 확인했다. 이 조사는 배포된 서버를 실행하거나 변경한 결과가 아니다. 구현하는 checkout의 최신 상태를 다시 확인한다.

| 확인한 코드 | 현재 동작 | 이번 설계에 필요한 변경 |
|---|---|---|
| SneakerDetailScreen.kt의 enhanceOpen | SUP 비용을 보여주는 확인 모달 | 독립 강화 화면으로 진입, 선택/최종 확인 시트 |
| ItemsViewModel.upgrade(id) | 대상ID만 repository로 전달 | 대상과재료3개,견적버전,요청키를 다루는 상태 |
| EconomyApi.upgrade(id) | sneaker_upgrade RPC에 p_id만 전송 | 재료·확률·소각·결과조회 계약 필요 |
| SneakerRepository.upgradeOnServer | 기존 대상 강화 호출과 조회 | 한 요청의 결과 복구, 서버의 일관된 결과 반영 |
| migrations/0023_sneaker_ops.sql의 sneaker_upgrade | SUP 차감 후 level+1 | 재료검증/소각/확률판정/결과기록을 일관되게 처리 |
| Sneaker.maxLevel와Rarity | 일반10/레어15/에픽20/레전더리30 및 서버 상한 | 새 강화상한20을 서버와함께 적용; 기존 자산수치는 보존 |
| MyShoesModel.StatScale | 효율표시27.5,착화감20 | 표시스케일은 재사용; 강화레벨분모20과 혼동 금지 |

현재 검색 범위의 후속 migration에서 재료ID/강화요청 결과계약을 확인하지 못했다. UI의 재료3개를 고르게 한 뒤 기존 p_id 호출만 보내는 것은 새 규칙 구현이 아니다. 클라이언트에서 임의 추첨하고 재료를 먼저 삭제하는 것도 허용하지 않는다.

UP12(사전재료거절), UP14(미전송), UP15(결과불명)는 실제 요청 상태를 구분할 수 있는 계약이 필요하다. 타임아웃만으로 미전송이나 실패라고 결론내리지 않는다. 지원되지 않는 동안 거짓 결과를 표시하지 않고 연결되지 않은 부분으로 보고한다.

성공 증가량(+1레벨,+0.5%p효율,+0.2%p착화감)과 실패 시 대상 유지에는 기존 제안이 포함된다. 사용자가 직접 정한 것은 하위등급재료3개,최대20,기본100−3L,실패도재료소각이다. 보정식은 사용자가 설계를 맡긴 범위의 기준안이다. 새 계약에 이 기준안을 반영하되 기존 레벨파생 수치와 중복 증가시키지 않는다.

앱을 읽어 조사했으며 변경·빌드·배포·경제 요청은 하지 않았다. 후속 구현은 현재 저장소의 AGENTS.md 및 redesign 문서를 함께 따른다.
