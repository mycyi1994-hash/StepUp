## 2026-10-04 재료 규칙 변경 (사용자 결정 · 서버 규칙 `forge-v2`)

원문(CLAUDE-HANDOFF.md · balance-rules.json 의 원래 키)의 "하위 등급 신발만 · 등급 차 계수 1 · ½ · ¼ · 일반 등급 강화 불가"는 아래로 바뀌었다.
balance-rules.json 맨 앞 `ruleChange20261004` 가 같은 내용이다.

- 재료는 대상보다 **한 등급 아래 · 같은 등급 · 더 높은 등급**. **두 등급 이상 아래는 쓸 수 없다**(서버 `GRADE`, 화면 "두 등급 이상 낮아요").
- 그래서 일반 신발도 강화할 수 있다 — 서버의 `LOWEST_GRADE` 막힘을 없앴고 시안 17(최하위 등급 강화 불가)은 해당 없음.
- 재료 한 개의 보정(천분율) = step × k / 2
  - step = 20 + 4 × (min(재료 레벨, 20) − 1). 재료 레벨은 1 이상이어야 하고(아니면 `LEVEL`), 20 을 넘으면 막지 않고 20 으로 센다.
  - k = 등급 차이(재료 − 대상): −1 → 2 · 0 → 3 · +1 → 4 · +2 → 5 · +3 이상 → 6. −2 이하는 재료가 아니다.
- 기본 = max(0, 1000 − 30 × 현재 레벨), 최종 = min(1000, 기본 + 재료 3개 합). 서버(`economy.forge_bonus_permille` 등)와 앱(`ShoeForge.bonusPermille`)이 같은 정수식.

| 재료 등급 − 대상 등급 | k | Lv1 | Lv5 | Lv10 | Lv20 이상 |
|---|---:|---:|---:|---:|---:|
| −1 한 등급 아래 | 2 | +2.0%p | +3.6%p | +5.6%p | +9.6%p |
| 0 같은 등급 | 3 | +3.0%p | +5.4%p | +8.4%p | +14.4%p |
| +1 한 등급 위 | 4 | +4.0%p | +7.2%p | +11.2%p | +19.2%p |
| +2 두 등급 위 | 5 | +5.0%p | +9.0%p | +14.0%p | +24.0%p |
| +3 세 등급 위 | 6 | +6.0%p | +10.8%p | +16.8%p | +28.8%p |

예: 레전더리 Lv10(기본 70.0%) + 에픽 Lv10 5.6 · 에픽 Lv1 2.0 · 레전더리 Lv1 3.0 = **80.6%**. (v6 예시의 레어 Lv10 은 두 등급 아래라 이제 재료가 아니다.)
이 표는 개발용이다 — 앱에는 계산표 · 계산 설명(16)을 넣지 않고 재료별 추가 성공률 · 최종 성공률 · 소각 안내만 보인다.

바뀌지 않은 것: 재료 3개 · 성공 · 실패 모두 소각 · 최대 Lv20 · 서버 판정 · 요청 키 · 결과 미확인 복구 · 클라이언트가 결과를 만들지 않음 ·
나머지 재료 막힘(없음 · 대상 자신 · 판매 중 · 착용 중 · 시작/가져온/발행 신발 · 체인) · 대상 막힘(없음 · 사용 불가 · 예전 신발 · 최대 레벨).

## 흐름

신발 상세 → 강화하기(경로 `sneaker/{id}/upgrade`) → UP01 → 빈 슬롯 + → UP02 재료 선택(하단 시트) → 선택한 n개 넣기 → UP03 →
강화하기 → UP04 최종 확인(하단 시트) → 강화 시작 → UP05 → UP06 성공 / UP07 실패. 뒤로는 상세로.
결과를 모르는 요청이 있으면 상세의 강화하기 자리가 "강화 결과 확인"이 되고, 같은 화면이 같은 요청의 결과만 묻는다.

| 시안 | 앱 상태 (`ShoeUpgradeState`) |
|---|---|
| UP01 · 03 · 08 | `UpgradePhase.Editing` — 적용한 재료 0 · 3 · 1~2개 |
| UP02 · 09 · 10 · 11 | `UpgradeSheet.Picker` + `MaterialsLoad.Ready(목록)` · `Ready(쓸 수 있는 것 없음)` · `Loading` · `Failed` |
| UP04 | `UpgradeSheet.Confirm(서버 견적)` |
| UP05 | `UpgradePhase.Running` |
| UP06 · 07 | `UpgradePhase.Succeeded` · `Failed` — 서버가 확정한 결과만 |
| UP12 | `UpgradeSheet.Changed` — 실행 전 확인에서 쓸 수 없게 된 재료(이미 선택에서 뺌) |
| UP13 · 18 | `UpgradePhase.Blocked(MAX_LEVEL · TARGET_UNAVAILABLE/TARGET_GONE/LEGACY)` |
| UP14 | `UpgradeSheet.Offline` — 요청을 보내지 않았다고 확실할 때 |
| UP15 | `UpgradePhase.Unknown(저장한 요청)` — 같은 요청 키의 결과만 다시 묻는다 |
| UP17 | 없음(2026-10-04 재료 규칙) |

재료 선택 목록은 쓸 수 있는 것 먼저 · 보정이 큰 순이다(서버도 같은 순서로 준다). 줄마다 추가 성공률과 대상과의 등급 차이
(한 등급 아래 · 같은 등급 · 한/두/세 등급 위), 쓸 수 없으면 까닭을 보인다.

## 규칙 (서버 `supabase/migrations/0054_shoe_forge.sql`, 앱 `domain/ShoeForge.kt`)

- 상한 Lv 20. 확률은 천분율 정수로 계산 · 저장한다(80.6% = 806). 화면의 확률과 서버가 판정하는 확률이 같다.
- 재료는 소유 id 로 고른다(모델 번호 · 목록 순번이 아님). 성공 · 실패 모두 재료 3개 소각(주인 비움 · `BURNED`).
- 성공 시 레벨 +1. 효율 +0.5%p · 착화감 +0.2%p(20% 상한)는 서버 실효 계산(`economy.sneaker_effective`)이 레벨에서 만든다 — 따로 더하지 않는다.
- SUP 요금 없음. 예전 SUP 강화(`sneaker_upgrade`)는 쓰지 않는다(설치된 예전 앱을 위해 서버 함수는 남겨 둠).
- 판정 · 소각 · 대상 갱신 · 기록은 `forge_start` 한 트랜잭션. 요청 키(uuid)는 앱이 보내기 전에 저장하고(`forge_pending`),
  같은 키는 다시 보내도 같은 결과를 돌려준다. 결과를 모르면 `forge_result` 로 같은 키만 묻는다 — 서버에 기록이 없으면
  그 키를 무효로 남겨 "받지 않음"을 확정한다(늦게 온 같은 키 요청도 실행되지 않는다).

### 재료가 될 수 없는 신발

두 등급 이상 아래 · 착용 중 · 판매 중 · 시작 신발(STARTER) · 가져온 신발(IMPORT · MINT) · 체인에 기록된 신발(토큰 있음 · 금고 발행 대기 ·
체인 작업 중) · 레벨 1 미만. 체인 신발은 계약에 소각 기능이 없어서 DB 에서 숨기는 것만으로 소각했다고 할 수 없기 때문이다(지시서 188행).

### 상한

모든 등급 20. 단 v3 금고 토큰 신발은 계약 상한(레어 15)과 20 중 작은 값 — 체인 값과 어긋나지 않게. 예전에 20을 넘은 신발은 레벨을 그대로 두고 강화만 막는다.
